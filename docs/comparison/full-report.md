## 2. 实验事故与处置：交叉污染（必须记录）

**首跑两组共用同一 project root，B 组被污染**，三重症状：

1. **读到 A 组的题**：B 组自述「到场发现你已发 16 题（Q1–Q16），我独立走查后补发 5 题」
2. **借用 intent-gate 方法论**：B 组自动加载了 `doc-analysis-playbook`（DSH 里 skill 按描述自动匹配，物理上难以隔离），并按"坐标/落点/L20"等 intent-gate 术语回报
3. **破了自身特性**：grill-me 本应 stateless，B 组却调 `dispatch_question` 把 5 题写进了 A 组的账本，还落了 `review-supplement.md`

**处置**：
- 污染产物移入 `_harness-vault/contaminated-group-B/`（留作证据，不计入对比）
- A 组成果备份 → 清空 kimi-02 → 恢复干净起点
- **硬隔离**：把 5 个 intent-gate skill 移出 `~/.dsh/skills`（B 组无法再"借用"方法论）
- 两组改为**时间串行**：B 组跑完才恢复 A 组产物，物理上不可能互相看见
- 重跑后 B 组：零落盘、未越界、未加载外来 skill ✅

> **副产品洞察**：DSH 里 skill 会按任务描述自动加载，**用 prompt 约束"禁止加载某 skill"是不可靠的**，必须做文件系统级隔离。这条对任何多插件对比实验都成立。

### 3.4 主指标的校准：红蓝对抗给出的反证

主指标（提问次数）衡量的是**检出广度**，**不是交付质量**。本次红蓝对抗（详见 §5.6 与 `_redblue-result.md`）给出了直接反证：

| 阶段 | A 组当时的"绿灯" | 独立蓝军实测 |
|---|---|---|
| 24 题全部核销后 | lint **CRITICAL 0**、`phase=deliverable`、报告自称「无未决题、无未确认推断」 | 第 1 轮查出 **6 CRITICAL + 16 MAJOR + 15 MINOR** |
| 37 条整改后 | 自称「**无未消 CRITICAL/MAJOR**」、lint CRITICAL 0、`deliverable: true` | 第 2 轮查出 **2 CRITICAL + 8 MAJOR + 8 MINOR**，且**实测推翻其两处自述**（`:22` 与 `:43`） |
| 终轮闭环率 | — | **严格口径 72.7%**（16/22），其中 5 条属"改了文字没改图"的半闭环 |

**三条推论**：

1. **A 组的提问是有效的，但不够**。24 题确实挖出了大量真实断层（含 6 处只有绘图才能逼出的失败边空洞），但产物仍带着 **6 条 CRITICAL** 交付——其中 2 条的病因是**人类已拍板的口径没有落实到图里**（R2-1 状态机仍执行被否决的越权置失效、R2-2 在放款结果未知时置成功终态）。**问对了问题 ≠ 把答案落对了地方。**
2. **lint 绿灯是"下限"不是"验收"**。CRITICAL 0 与"状态机边动作仍在执行被否决的口径"可以同时成立——因为 L21 只校验状态存在性、不校验边与边动作（工具缺陷 #1）。
3. **两个插件都缺"独立对抗方"**。intent-gate 把红蓝对抗做成了**可选插件**（本次是用户主动点名才跑，默认不启动），grill-me 则完全没有等价机制。而**只有独立视角能抓出"同视角盲区"**：F-2（编排者废弃断层时只想着"不计入统计"）、F-1（红军自己看到 `tables=6` 却没追问"登记 4 张表为何得 6"）、R2-1/R2-2（改文字不改图）——**这三类错误在作者自己的视角里都不可见**。

**对主指标读法的修正**：提问次数应读作「**检出广度**」，不能读作「对齐质量」。一个 agent 问 10 题还是 24 题，都不能替代"换一个视角去查它"。这也是本次对比最重要的方法论结论。

### 4.4 A 组 MCP 额外 token 开销估算

**数据来源**：`~/.dsh/sessions/--F-mcp-intent-gate--/c0cc6b3c.../session.v4.jsonl.zstd`（zstd 解压后 2,451,612 字符 / 802 条记录），含**完整工具定义**（`request/header` 36,602 字符）、**105 次请求的真实 usage**、**173 次工具调用与返回**。统计脚本：`_mcp_overhead.py`。

**口径**：只计 MCP 带来的额外开销 —— ① 14 个 `mcp__intent-gate__*` 的工具 schema（每次请求都随 system 一起发送）；② MCP 工具的入参与返回。**不含** playbook/skill 内容（那属方法论成本，非 MCP 机制成本）。

| 项 | 值 |
|---|---|
| MCP 工具定义（14 个 schema） | **12,294 字符 ≈ 4,928 tok**，占全部工具 schema（36,602 字符）的 **33.6%** |
| MCP 调用次数 | **71 次**（占全部 173 次工具调用的 41%） |
| 入参合计 | **18,734 tok** |
| 返回合计 | **24,245 tok**（46,326 字符） |

**最贵的 4 个工具**：

| 工具 | 次数 | 入参 tok | 返回 tok | 说明 |
|---|---|---|---|---|
| `list_pending_questions` | 6 | 123 | **14,182** | **最大返回项** —— 每次回吐整份待决清单（约 3,700 字符/次） |
| `dispatch_question` | 26 | **9,147** | 1,574 | 入参最大：每题要带完整题面 + 4 选项 + 推荐 + 目标角色 |

| **[C] 返回内容累积重发** | **≈ 1,260,800 tok** | result 一旦进历史，后续每轮都重发（按平均剩余 52 轮加权） |
| **[B+C] 合计** | **≈ 1,796,900 tok** | — |

**占真实总输入的比例**：A 组真实累计输入 **15,660,877 tok**（其中 15,553,152 为 cacheRead，占 99.3%）

- 工具定义累计 517,400 → 占 **3.3%**
- 返回内容累积 1,260,800 → 占 **8.1%**
- **MCP 机制合计 ≈ 11.4%**

> **读法提示**：占比看着不高，是因为 A 组把大量篇幅花在**读 playbook、读 wiki、读源码**上（那是方法论成本）。若只看"MCP 机制本身"，**每 9 个输入 token 就有 1 个是 MCP 带来的**。且 99.3% 命中 cache，**按缓存价格计费时实际成本占比会远低于 11.4%**；反之若未命中缓存，MCP 部分的绝对成本会显著放大（约 180 万 token 量级）。
>
> **估算局限**：① token 数由字符数换算（CJK≈1 tok/字，其他≈3.5 字符/tok），非真实分词器，误差约 ±10–15%；② 口径 [C] 假设 result 在后续轮次中均匀分布，实际越晚产生的 result 重发次数越少，故 [C] 偏保守（偏高）；③ 未计入 5 次 `abandon_question` 之外的失败调用。

## 5. 关键发现

1. **「绘图探测」是阅读层无法替代的仪器**。A 组自评：22 条断层里，阅读层 16 条、**绘图层 6 条**，而后者**全部是失败边空洞**——PRD 只写正常流，阅读层对"失败后去哪"是**结构性盲**。最典型的是"提交失败哪些可重试"：PRD §5 说"网络失败→提示重试"，读起来毫无异常；画「提交中」的出边时才被迫发现它与 wiki"流程推进失败置 TERMINATE 不可重试"**语义互斥**。

2. **「代码实证分流」不是 intent-gate 的专利**。两组都主动读了 `wiki/领域术语.md` 的提现域 24 条术语，都用它消解了 6–8 个 PRD 疑点并**明确声明"不该再问人"**。真正的差异不在"会不会查代码"，而在**查完之后是否强制落盘、是否有门禁**。

3. **grill-me 的独门武器是「对答案做反向一致性校验」**。B 组收尾时把业务方批复逐条与知识库交叉验证，挖出 3 项"答案本身有洞"——尤其术语表冲突那条，A 组**在 24 题里没问**。这是"追问式"方法论的自然产物：它把每个答案都当成下一个问题的输入。

4. **intent-gate 的独门武器是「复核补题 + 硬门禁」**。它在 Phase B 回头审查自己收到的答案，抓出**自己的过度消除**（"我把 INVALID 枚举存在当成触发条件已定"、"我把'有哪些步骤'当成'什么条件跳哪个'"），并把每一条**变成可追踪的题**；不闭环就 `blocked`，且**拒绝自授 approved**。

5. **提问数不是越多越好，但"能否把发现变成强制闭环"是分水岭**。B 组同样发现了洞（3 项回补），但它写成了"下一轮建议"——**不闭环也能宣告完成**；A 组则把自己锁死在 `blocked` 直到 24 题全清。

6. **产物可传递性决定了下游是否还要重新问一遍**。A 的 **82KB 契约 + 74 锚点**可以让编码 agent 直接消费；B 的成果停在对话里，换一个会话就归零（grill-me 自称 stateless 是特性，但在"需求→编码"链路上是代价）。

## 5.5 单列观察：lint 门禁的覆盖边界（**非对比项**）

> ⚠️ 本节**不属于意图对齐能力的对比结论**——SQL/DDL 是 A 组单侧产物，B 组无从对比。仅作为对 intent-gate **门禁可靠性**的单项观察记录，不影响 §6 的选型结论。

验收时对 A 组产物做了一次**独立复核**（不看它的自评，直接数磁盘文件），发现：

| | |
|---|---|
| `summary.md` §3.4 登记 | **4 个 DDL**：`t_sign_order` / `t_sign_order_fund` / `t_pre_cost_info` / `t_withdraw_optional_period` |
| `sql/` 目录实际 | **只有 2 个**：`t_sign_order.sql`、`t_withdraw_optional_period.sql` |
| 缺失 | **`t_sign_order_fund.sql`、`t_pre_cost_info.sql`** |
| 而此时 `lint_summary` 报 | **CRITICAL = 0** ✅ |

**这说明什么**：`lint-report.md` 里 L9 的判定契约是「出现 `\bsql/` 登记时，`sql/` 目录必须存在且含 `.sql` 文件」——**它只校验"目录非空"，不校验"登记清单里的每个文件是否真实存在"**。

于是出现了 README 里最不愿看到的那类失效：**「机械强制」给了一个 CRITICAL 0 的绿灯，但交付物是残缺的**。

这条对本报告的核心论点构成重要补充，必须诚实地列为 intent-gate 的局限：

1. **机械门禁只能查"可形式化"的问题**（状态机有无终态、有无死状态、锚点格式、占位符残留、BR 引用完整性），**查不出"文档声称 vs 磁盘实际"的一致性**。后者需要**另一个视角的独立复核**。
2. 这正是 playbook 把 **蓝军独立评审**列为"第 ④ 层探测器"的原因——它要抓的正是"作者注意力之外的系统性盲区"。本次是编排者（我）在做交付验收时偶然抓到的，**若只信 lint 绿灯就会漏掉**。
3. 对 grill-me 一侧的公平说明：**grill-me 根本没有门禁，因此它不存在"假绿灯"问题**——它的短板是另一个维度的（无产物）。但"有门禁"也绝不等于"可以不做独立验收"。

> 建议的规则补强（一句话）：L9 应从"目录非空"升级为"**summary 中登记的每个 `sql/<name>.sql` 路径都必须实际存在，缺一即 CRITICAL**"。

**A 组的处置（值得完整记录）**：
1. 补齐 2 个 DDL（`t_sign_order_fund.sql` 2845B / `t_pre_cost_info.sql` 3098B），字段与 §3.4 映射矩阵逐项对齐，含枚举注释与索引；`tables` 计数 4 → 6，重跑 lint 仍 CRITICAL 0
2. **不靠推测，做对照实验证实盲区**：把 `t_pre_cost_info.sql` 临时移出 `sql/` 后重跑 lint —— **仍是 CRITICAL 0**，只有 `tables` 从 6 掉到 5，而该计数不触发任何门禁；恢复后回到 6。证据链闭合，证明是**规则契约覆盖范围问题**而非漏跑规则
3. **主动修正表述**：把"lint CRITICAL = 0"改述为"**在其机械判定契约（L1–L22）覆盖范围内** CRITICAL = 0；该结论不覆盖报告内文本登记的完备性，完备性由宿主逐项人工核对，本轮曾漏核 2 个 DDL 并被验收方发现"
4. **自查出第二处同类问题**：`draft_mapping` 脚本报 `unresolved: 0`，但复核发现 **2 处锚点误定位**（Q2 被"前置费用"关键词误配到 `提交中-->前置费用等待`；Q14 被"初始化"误配）—— 同样是「工具报绿 ≠ 语义正确」
5. 把缺陷与教训固化进 `analysis-draft.md` §九，并如实记录「**该缺陷由验收方发现，非工具发现、亦非宿主自查发现**」，未作淡化

**对本报告的启示**：intent-gate 的机械门禁是**下限保障**而非**验收标准**。它擅长抓"可形式化的结构错误"，但抓不出"文档声称 vs 磁盘实际"的一致性——**这类问题必须由另一个视角复核**。这也从反面印证了 playbook 为何把「蓝军独立评审」列为第 ④ 层探测器。

## 6. 结论与选型建议

### 6.1 只看"提问与产物"两维度时的结论

**如果目标是"需求要交给另一个 agent 或另一个人去实现"** → 选 **intent-gate**。它多花的提问成本（约 2.4 倍）换来的是可机检、可追溯、带门禁的契约；没有产物，对齐成果无法传递。

**如果目标是"我自己要想清楚一个模糊想法 / 评审一个已有方案"** → 选 **grill-me**（更准确说是 `grill-with-docs` 变体）。它提问更少更聚焦，且会反向挑战你已有的答案——本次它抓出的术语表冲突，是 intent-gate 24 题都没覆盖的。

### 6.2 加入红蓝对抗后：结论被显著修正

主指标只能度量**检出广度**。红蓝对抗（§5.6）证明：A 组问满 24 题、lint CRITICAL 0、报告自称"无未决题、无未确认推断"之后，独立蓝军**仍查出 6 条 CRITICAL**；整改后自称"无未消"，**又被查出 2 条 CRITICAL、且两处自述被实测推翻**。

| | A intent-gate | B grill-me |
|---|---|---|
| 有无**独立对抗**机制 | **有**（`red-blue-review` 可选插件） | **无任何等价机制** |
| 本次是否启用 | 是（**用户主动点名**才跑，默认不启动） | — |
| 对抗实测效果 | 第 1 轮 37 条 → 5 道裁决题（Q31–Q35）→ 逐条闭环（严格闭环率 **72.7%**）→ 终轮 2 条 CRITICAL → 修复 → **人类实测验收放行** | 其"3 项回补清单"是**自我校验**，未经独立验证 |
| 对抗抓出的关键缺陷 | ① 状态机仍在执行**人类已否决**的越权置失效口径；② **放款结果未产生**就置成功终态（资金单据终态造假） | 未验证 |
| 未启用时的后果 | **那 6 条 CRITICAL 会原样进入编码阶段** | 未知 |

**这一段是本次实验最有价值的发现**：抗机制**确实有效**（它把缺陷一路推到"删状态、FINISHED 收敛为唯一写入点"的实质修复，而不是文字游戏），但它**默认关闭**——**质量门存在 ≠ 质量门被使用**。

### 6.3 修正后的选型建议

**要交付给别人实现** → 选 **intent-gate，并强制开启红蓝对抗**。它带来的契约是唯一可传递的形态，但契约本身会带伤（本次 6 条 CRITICAL，且 lint 全绿），而它自带的对抗插件是唯一能把这些伤逼出来的机制。**只装插件不跑对抗，等于买了保险不生效。**

**要自己想清楚一个模糊想法** → 选 **grill-me**。它提问少而聚焦，会反向挑战你已有的答案。但必须意识到两点：**产出没有第三方验证，也没有产物可传递**——换一个会话就归零。

**修正后的最优实践（三段式，缺一不可）**：
```
grill-me（发散：把想法问清楚）          ← 决策树前沿，问得准
   → intent-gate（收敛：落成契约）      ← 契约固化，lint 归零
   → red-blue-review（对抗：换视角查）  ← 唯一能抓「同视角盲区」的一环
   → 编码
```

### 6.4 一句话结论

**提问能力两个插件都有；独立对抗只有 intent-gate 有，而且默认关闭。** 本次实验最有价值的发现不是"谁问得多"，而是——**问满 24 题、lint 全绿、自称无未决之后，产物仍然带着 6 条 CRITICAL 准备交付**。任何"对齐已完成"的自证，都必须由另一个视角来验伪。

## 8. 本次实验的局限

1. **业务方由编排者扮演**：答案取自既有答案卡（保证口径一致），但"PM 现场拍板"的部分由我代拟（如 Q19 强制支付开关语义）。
2. **批量提问的调整**：grill-me 原版要求"一次一题"，为控制往返轮次，两组均允许多题批量提交——这是对原生行为的对称修改。
3. **串行而非并行**：因首跑污染，重跑改为串行，两组未在同一时刻运行（不影响对比有效性，但耗时翻倍）。
4. **wiki 降低了区分度**：kimi-02 自带提现域术语表，消解了约半数技术断层；若换一个无知识库的项目，intent-gate 的"代码实证分流"优势会更明显（或反之，提问数都会大幅上升）。
5. **红蓝对抗的独立性仅达最低门槛**：蓝军与红军同为 deepseek-flash（**同厂商异 session**），满足 skill §1「同厂商异 session 即可」的 🟡 要求，未采用异厂商模型（skill 列为加分项）。且双方由**同一编排者**调度与投喂材料，编排者的判断偏差理论上可能同时影响两侧——本次已通过"蓝军只读产物、禁止索要红军推理"来约束，但无法完全消除。
6. **红蓝对抗只跑了一轮整改**：终轮 FAIL 后按熔断交人类裁决，修复结果由**编排者实测验收**（非蓝军复评）。也就是说，最终的"放行"判断来自人类侧而非独立蓝军——这符合 skill 的"approved 只有两条路"（蓝军 PASS 或人类拍板），但强度弱于蓝军 PASS。
5. **单次实验**：n=1，两组各跑一轮，未做重复实验；结论应视为**定性方向**而非精确统计。
